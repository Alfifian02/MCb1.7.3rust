# Roadmap part: performance and memory

Part of [`ROADMAP.md`](../ROADMAP.md). This part holds the open speed and memory work (the renderer rewrite's next steps, the Sodium audit, the memory audit) and the changelog of the ports that did it: C2ME (workers for meshing, light, I/O, populate, lazy noise), Embeddium / Sodium (arena, 16-byte vertices, occlusion culling), Radium, ModernFix, Noisiumed, FastNoise, FerriteCore, frame-cost passes, culling.

## Memory and speed: what is still missing (follow-up of the FerriteCore audit, 2026-10-21)

Nothing here is written. None of it was measured: there is no phone and no Rust toolchain in the sessions that audited it, the sizes come from the code. Per loaded chunk the arrays are `blocks` 32 KB + `light` 32 KB + `data` (metadata, now lazy) 16 KB at most, and the light thread holds a second copy of `blocks` and `light`. Do 1 first; the rest in this order (smallest and safest first).

1. **Measure.** RSS at the usual render distance on the phone, split into chunk arrays, LoD tiles (`KEEP_TILES` 600) and GPU pages. Every item below is a guess until this exists.
2. **One copy of `blocks` / `light` for the render thread and the light thread** (`Entry.blocks` / `Entry.light` vs `LChunk.blocks` / `LChunk.light`, 64 KB a chunk twice over). `Arc<[u8]>` with `Arc::make_mut` on every write; the writers are `ChunkManager::set_block*`, populate (`put_region`), the light thread's `Report`. This is the upgrade the `ponytail:` note at `MeshJob` already names, and it also removes the `Snap` copy of a mesh job (5 x 80 KB, memcpy speed on the render thread).
3. **Light reports as deltas.** `Report.chunks` sends the whole 32 KB light array of every chunk touched in a 5 ms slice (`LIGHT_SLICE`); send the changed range, or the section, instead.
4. **Neighbour slabs for mesh jobs.** The mesher reads a neighbour chunk only through `rid`, `meta_at` and `lv` at `x` or `z` in `-1..=16`, which is one border plane (x = 15 or 0, z = 15 or 0). Snapshotting that plane (about 5 KB) instead of the chunk (80 KB) is ~100 KB a job instead of 400 KB. Needs a new `build_split_tinted` argument type and edits to its ~40 tests; skip it if 2 lands (the copy is gone then).
5. **Per-section storage of `blocks` and `light`** (FerriteCore's single-value `PalettedContainer`): a 16-high section that is all air, all stone or all sky light is one value. The big saving (about half of a chunk's arrays), and the invasive one: the index is `(x << 11) | (z << 7) | y` with `y` fastest, so a section is not contiguous, and every reader takes the raw slice (`mesh`, `light`, `save`, `populate`, LoD ingest). Its own milestone, with the save format converted on load and save.
6. **Section-level lazy `Nibbles`.** Metadata is lazy per chunk since 2026-10-21 (no array while all 0); per 16-high section would keep 2 KB where a chunk has only ground-level tall grass. Needs a private layout and `bytes()` building the McRegion order (used by `save` and the golden hash in `populate`).
7. **LoD memory.** `Span` is 7 bytes of which 3 are a tint that is white for everything but grass and leaves: a palette index makes it 5; `Cell` is 24 bytes (`x`, `y`, `z` as `i32`); `Tile.cov` is a `Vec<bool>` (a bitset is 8 times smaller); identical columns could be interned (the hit rate on natural terrain is probably low: measure).
8. **Cheaper hashing outside the chunk map.** `ticks.rs` (`pending`, `notes`) and `gen/overworld.rs` (`cols`) still hash with SipHash; `chunks.rs` has a `KeyHasher` for this. Speed, not memory; small.

## Renderer rewrite (lightweight frame)
- Frame = 3 render passes: scene (sky, solid, far terrain, cutout, entities, water, rain) into an 8-bit sRGB target at `RENDER_SCALE`; pass A FXAA + CAS at scene size; pass B upscale + vignette + HUD (`render/present.rs`). Depth is `Discard`ed.
- Chunk shader (`gpu/pipeline.rs`) lights and fogs per VERTEX like b1.7.3; one atlas read per pixel; Sodium-style layers: `solid` (no `discard`, tiler HSR works), `cutout`, `lod`, `water`. `build_job` splits the triangles by tile alpha (`atlas::is_cutout`); `draw_ranges(Layer)` walks a near-to-far order cached once a frame.
- Removed: Photon (G-buffer, deferred, shadow maps, VL, GTAO, clouds, HDR post chain, pack/fog/noise) and its assets' code paths. `render/color.rs` keeps `legacy_lin`. `LEGACY` stays as a switch for the mesher and the sky.
- Not measured on a device (no phone here); verified by `cargo test` on lavapipe (`frame_renders_headless`, shader validation, `is_cutout`).

### Not done / next (in this order)
1. **Measure on the phone.** Compare the `FPS:` / `CPU ms/frame` log line with the old build; CPU ~ frame time = CPU-bound (go to 2), far below = GPU-bound (go to 4).
2. **Chunk arena** — WRITTEN 2026-10-20 (not compiled, not run: see the changelog; the text below is the plan it followed, with the changes noted there): one big vertex buffer, one `set_vertex_buffer` per frame, one `draw_indexed` per section run. A shared quad index buffer replaces the per-chunk `ibuf` (the mesher emits 6 indices per quad; sort quads, not indices, by section). `base_vertex` needs `DownlevelFlags::BASE_VERTEX`: absent on a GLES 3.0 fallback, keep the per-chunk path there. Sodium's `RenderRegion` / `GlBufferArena` source helps here.
3. **16-byte vertices** (`embeddium/src/vertex.rs`): chunk-local u16 position + a per-draw origin, u16 uv, packed light/tint. Cuts vertex fetch and the varying traffic.
4. **Dynamic resolution**: move `RENDER_SCALE` between ~0.5 and 0.8 from the GPU frame time; pass A/B already follow `Gpu::scene()`. Alternative to pass B: let Android scale the surface (`ANativeWindow_setBuffersGeometry`), untested.
5. **Bake the face shade of flat faces** in the mesher/LoD (`push_face`, `lod::Quads`) so `flat_shade` (derivatives) leaves the fragment shader; needs a spare vertex field because far terrain keeps its tile in `light`.
6. **Per-frame CPU**: the HUD and the item/entity mesh are rebuilt every frame; mesh jobs copy a snapshot on the render thread; translucent water sorts whole chunks only (sections/faces keep map order).
7. **Dead code from the removal**: Photon sky in `sky.rs` (LUT, SH, `sky_sh.wgsl`, `scattering.dat`), assets only they read (`noise.rgba`, `noise_b.r8`, `worley_*.dat`, maybe `sky.rgba`), the 50 `cargo check` warnings (`Gpu::depth_copy` / `copy_depth` went with the GPUBooster port, 2026-10-21 (2)).
8. **Stale tests**: 8 fail in `render/mesh.rs`, `hud.rs`, `outline.rs` (they read vertices with stride 6, the vertex is 8 floats); not touched by the rewrite.
9. **Look checks on the device**: FXAA/CAS are lighter variants (4 diagonal taps) of the old ones; compare edges, distant leaves (alpha from mip 0 in `fs_cut`) and the sky/fog seam. MSAA 4x would be cheap on a tiler but is not wired.

### Sodium features still to port (audit of `sodium-dev`, 2026-10-20; read from file names and the mc-rs code, not from the Java bodies)
Already in: occlusion culling (`embeddium::cull`, `vis`), render layers solid / cutout / water (`TerrainRenderPass`), the buffer arena (chunk pages, see the 2026-10-20 changelog entry; not compiled yet). Measure on the phone first (step 1 above): if the frame is not CPU-bound, none of this pays.

Cheap, in this order:
1. **Shared quad index buffer** (`SharedQuadIndexBuffer`) - WRITTEN 2026-10-20 (not compiled, not run; see the changelog): one buffer of `0,1,2,0,2,3 + 4n` for every mesh instead of an index run per chunk; index memory down by about a third and no index upload. The mesher must emit quads sorted by section, not indices (`by_section` today sorts triangles). Needs `base_vertex` or one shared buffer per page sized to the page's vertex count; the pages already write shifted indices, so this replaces that.
2. **16-byte vertex** (`embeddium/src/vertex.rs`) - WRITTEN 2026-10-20 (not compiled, not run; same as step 3 above): chunk-local u16 position + per-draw origin, u16 uv, packed light/tint. Touches `Vertex::layout`, `vs_main`, `vs_water`, `build_job` and `Pages::put` (`VERT_BYTES`).
3. **Upload budget by size** (`UploadResourceBudget`, `MeshTaskSizeEstimator`, `UploadDurationEstimator`): `MESH_PER_FRAME` and `CHUNK_WORK_BUDGET` are fixed counts and times today; a byte budget per frame, fed by the measured cost of `write_buffer`, smooths the frames where many chunks finish at once.

Heavier:
4. **Async occlusion walk** (`CullTask`, `AsyncCameraTimingControl`): `update_visible` runs on the render thread every frame. Only worth it with a render distance well past 4 chunks.
5. **Per-quad water sorting** (`ChunkBuilderSortingTask`): water is sorted per chunk only (step 6 above). Sorting quads fixes blend artefacts but means re-uploading the water indices when the eye moves (they are a separate run of the page, so only that run is rewritten).
6. **Light data cache + smooth lighting** (`ArrayLightDataCache`, `SmoothLightPipeline`, `AoFaceData`): only if the mesher gets per-vertex ambient occlusion; the b1.7.3 look (light per vertex from the cell) does not need it.

Not applicable, left out on purpose: multi-draw and persistent mapping (not in wgpu's downlevel set, none on a GLES fallback), mixins and the Forge / Fabric glue, the options screen, `ColorProviderRegistry` (biome tints are `biome_tints` already).

- 2026-10-15: C2ME idea 5: lazy 3D noise in the terrain density (the last item of the C2ME audit; written WITHOUT a Rust toolchain: not compiled, not run; +2 tests `noise::tests::lazy_3d_noise_matches_the_original_algorithm` and `overworld::tests::lazy_density_matches_the_plain_computation`, not run; the real check is `overworld::tests::matches_java_reference`, which hashes terrain made through this path against the real b1.7.3 and must still pass). Source: C2ME's worldgen / math optimisations (`c2me-opts-math`, noise sampling): do less noise, same numbers.
    - Where the time goes (by counting, nothing was profiled on a device): `density` evaluates 40 octave passes of 3D Perlin over the 5x17x5 grid = ~17,000 samples at ~100 flops each (`noise_lim` 16 octaves + `noise_low` 16 + `noise_base` 8), the biggest single cost of generating a chunk; surface noise, climate noise, the cave tunnels and the column loops are each a fraction of it. Generation runs on the workers, so this speeds up how fast terrain appears (startup, walking), not the frame.
    - The saving: the blend in `density` takes `lim` alone where `mix < 0`, `low` alone where `mix > 1`, both only in between (`mix` comes from `noise_base`). Measured on a Python port of the generator (5 seeds x 8 chunks, 3400 points x 5 = 17,000 grid points): `mix < 0` at 42.6% of the points, `mix > 1` at 45.0%, both needed at only 12.4%. So 87.6% of the points need one of the two big stacks, i.e. 44% of the lim + low samples (80% of all 3D octave work) are never read. Per COLUMN the gain would have been only 13% (the sign of `mix` changes along y), so the mask is per sample.
    - How (merged 2026-10-16 into the Noisiumed column cache, which the first version of this patch predates): `mix` comes from `noise_base`, which belongs to the COLUMN, so the need flags are the same for every chunk that reads a cached column and the cache stays valid. `OverworldGenerator::column` fills `base` first, derives `need_lim = !(mix > 1)` and `need_low = !(mix < 0)` with the same expression the blend uses (a NaN needs both), and fills `lim` / `low` with the new `OctaveNoise::generate_masked_into`, which leaves the unwanted samples at 0.0 (never read). `PerlinNoise::add` became `add_masked(.., need)`; `add` is `add_masked(.., None)`. Bit-exactness hinges on one quirk of `NoiseGeneratorPerlin` that the port keeps: the four cell corners (`d1..d4`) are worked out at the FIRST y of a run of equal `yb` and reused, with that first y's fraction, for the rest of the run. So a sample's value depends on its run's first y even when that y is skipped: the run start's `yb` and fraction are remembered at every run start, and the corners are computed the first time a wanted sample of the run needs them (`fresh`). Every computed sample is the same f64 operations on the same inputs as before, so the same bits.
    - Tests: the noise test keeps a verbatim copy of the old 3D loop (`reference_add`) and compares `generate` (no mask) and `generate_masked` (5 masks, 4 scales including runs of one `yb`, masks that skip run starts, whole columns, everything) to it by `to_bits`; `overworld::tests::lazy_columns_match_the_plain_noise` compares a lazy cached column with a plain full one at every sample the blend reads (and checks that some were left out). RUN in a Linux scratch crate (rustc 1.75, `world/gen` + `chunk` + `biome`): these two, `matches_java_reference` (18 golden chunks), `cached_columns_match_a_fresh_generator`, the Tectonic and populate tests pass, so parity with the b1.7.3 Java holds.
    - ponytail: the cache and this mask multiply, but the cache's 30% is the best case (see the Noisiumed entry) and the mask's ~44% fewer lim + low samples is independent of chunk order. Not done: SIMD (Perlin's permutation lookups are gathers), the cave tunnels (their random draws must stay in order). UNVERIFIED on a device: the actual speed-up (by operation count about 18% of a chunk's generation).
- 2026-10-14: C2ME idea 4: the light engine runs on its own thread (written WITHOUT a Rust toolchain: not compiled, not run; tests changed or added in `world/chunks/light.rs`: `flat()` / `settle` now go through the thread, `relit_matches_the_plain_formula` now runs on `LightWorld` directly, +1 `light_thread_matches_the_engine` (the thread's result == the engine run directly, light + heights + blocks of every chunk after each of 7 edits), none run). Source: `c2me-threading-lighting`. This is the biggest change of the C2ME series: `light.rs` was rebuilt around a message protocol, read it before trusting it.
    - Design (nothing is shared, so there are no locks): `LightWorld` (the thread's) owns a COPY of every chunk's blocks and height map (`LChunk`) and is the only writer of the light; `ChunkManager` keeps a read-only copy of the light in `Entry.light` / `lit` that the thread's `Report`s replace. The render thread sends `Msg::Chunk(key, blocks)` (from `insert` and `put_region`: new, or rewritten by populate; the chunk is unlit until `Init`), `Msg::Edit {x, y, z, id}` (from `set_quiet`), `Msg::Remove(key)` (unload) and `Msg::Init(key)` (`light_pending`, up to 4 chunks per frame, only while the thread is settled), in the order they happen; the thread runs the old engine code (`update_region`, `relit`, `init_chunk`, ... moved from `impl ChunkManager` to `impl LightWorld`, bodies unchanged except where listed below) in 5 ms slices and sends a `Report` after each: the whole light array of every chunk it wrote to, its lit flag, the chunks whose mesh went stale (the old `mark_dirty` edge rule), and how many messages it has processed.
